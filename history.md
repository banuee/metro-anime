## 2. Что сделано в этой сессии

### 2.1 Диагностика «скачанное не играет»
Проверено на живом устройстве:
- Файл в галерее валиден: `ffprobe` даёт 2 трека (H.264 640x360, AAC-LC 44.1kHz), 1374 с.
- MP4 **некорректен по таймлайну**: `stts` состоит из тысяч записей с дельтой 9 (100 мкс) вместо
  равномерных 3754, а `ctts` содержит 29 909 записей с офсетами ~11280 (3 кадра). Почти все
  PTS немонотонны (14 564 из 32 944) — это следствие того, что в MPEG-TS PTS не монотонны (B-кадры),
  а `MediaMuxer` не умеет с ними работать и пишет сломанные таблицы.
- Media3 (`Mp4Extractor`) на таком файле зависал: `state=BUFFERING`, `position=0`,
  `buffered=72947` — бесконечная загрузка. Онлайн-HLS при этом играл нормально (`state=PLAYING`).
- Логи плеера показали: AAC-декодер получает 1947 буферов и **0 выходов** → аудио-рендерер стоит,
  а playback clock (он же привязан к аудио) не двигается → позиция 0.

### 2.2 Переписан ремукс TS→MP4 (`data/download/HlsDownloader.kt`)
- Два прохода по TS: первый собирает статистику (число сэмплов, длительность, число ADTS-кадров),
  второй пишет MP4.
- Видео: **равномерный CFR-таймлайн** (длительность кадра = span PTS / (N-1)) вместо исходных PTS —
  файл получается стандартным, `ctts` пустой, `stts` равномерный.
- Аудио: ADTS-кадры из одного сэмпла **разделяются** на отдельные AAC-фреймы, в MP4 пишутся
  **без ADTS-заголовка** (payload), плюс добавляется `csd-0` = AudioSpecificConfig (0x11 0x90 для 48 кГц стерео),
  иначе декодер AAC не может сконфигурироваться.
- **Важный грабли:** в первом проходе нельзя забывать `extractor.selectTrack(...)` — без него
  MediaExtractor отдаёт один и тот же сэмпл, и весь таймлайн схлопывается (получился файл длиной 3.7 с).

### 2.3 Добавлено логирование (временно, можно оставить или убрать)
- `PlayerScreen`: `resolve:` (найден ли офлайн-файл и какой URI), `resolve online keys=...`,
  `feed url=... seek=...`, `state=... pos=... buffered=...`, `tick:` (каждые 3 с), `player error:`.
- `HlsDownloader`: `remux plan: video=... frame=...us audio=... adts frames frame=...us`.

### 2.4 Проверенные на устройстве факты

- Офлайн-файл **после переписывания ремукса**: `dur=1540820` (25:41) — длительность верная,
  `state=READY`, `playing=true`, но `position=0` и снова уход в BUFFERING.
- **Текущий статус по жалобе пользователя:** файл скачался, видео идёт, но примерно 3 fps и **без звука**.
- `ffprobe` на новом файле: структура правильная (видео 36 925 кадров по 41.7 мс, аудио 72 244 кадра по 21.3 мс),

## 3. Что осталось по багу воспроизведения (главный приоритет)

Гипотеза (проверить в первую очередь): **ADTS-заголовки в исходном TS врут** —
в них `profile field = 1` (AAC-LC), а фактически payload содержит AAC-LTP
(ffmpeg: «Prediction is not allowed in AAC-LC»). Тогда:
1. Собрать ASC с object type 4 (LTP) вместо 2 (LC) и записать в `csd-0`;
   либо
2. Определить профиль честно (например, попробовать декодировать кадр и посмотреть на ошибки);
   либо
3. Как страховка: **откатиться к хранению .ts** и отдавать в плеер TS-файл (media3 TS-экстрактор
   этот поток играет корректно, т.к. онлайн-HLS с тем же источником работает) —
   но тогда файл не виден в галерее. Компромисс: MP4 для галереи + TS для плеера (расход места ×2).

Дополнительно проверить:
- Правильность разбиения ADTS: сейчас при рассинхроне ищем первую «0xFFF» и идём от неё;
  возможно, нужна непрерывная walked-разбивка по `frame_length` от начала сэмпла
  (иначе кадры смещаются → мусор в битстриме).
- После починки аудио проверить, уйдёт ли «3 fps» (похоже на побочный эффект мёртвого аудио-рендерера).

### 7.1 Точная диагностика аудио (новые факты, опровергают гипотезу LTP)
- Анализ MP4-файла «Голубая шкатулка» (новый ремюкс) по сэмплам:
  - esds ASC = `11 90` → **AAC-LC, 48 кГц** — buildAsc отработал как задумано, csd-0 записан.
  - **97 % аудио-сэмплов НЕ начинаются с ADTS-синка** (`FF Fx`): у первого — мусорный префикс `00 ...` (виден ASCII `Lavc62.11.100` — это заголовок 16-байтной структуры ffmpeg, рядной метки кодека у сегмента kodik/ffmpeg 8), у остальных — «сероватые» 5-байтовые префиксы вида `48 00 00 xx FF...`: синк внутри сэмпла на +5 до +302 байт. 3888 из 4000 сэмплов «sync-late», 112 — без синка вообще.
  - Значит **MediaExtractor отдаёт аудио-сэмплы MPEG-TS со СДВИНУТЫМИ границами** (не по ADTS-кадрам, а по PES-обрывам TS). Раз наша старая разбивка `splitAdtsFrames` от начала сэмпла упирается bytes sync и почти всегда даёт 0 кадров → в старом коде `frames.isEmpty()` → писался ВЕСЬ сырой сэмпл (ADTS-заголовок ВНУТРИ MP4-сэмпла + мусор) → декодер AAC выдаёт сплошные ошибки: «Prediction is not allowed in AAC-LC», «channel element 2.4 is not allocated» (ffmpegsdecode-тест 10 с: Decode error rate 0.999986 → ~1 руб. из 10 с звук нормальный, всё остальное мусор).
  - Пока ffmpeg сыплет ошибки, AAC‑рендерер всегда стоит, и из-за этого же оно тормозит «3 fps» (аудио-висяк душит clock).
- В старом (до rewrite) ремюксе «Чёрный клевер»: аудио-сэмплы целиком от extractor'а с НЕСБИТЫМИ ADTS-заголовками `ff f1 50 80 21 9f fc` (ADS → профиль Main (0), freq_index=7=22050), крупные 2.7 КБ сэмплы; но ffmpeg всё равно них decode не подтвердил.
- carve-тест (carve_aac.py) на «Чёрном клевере»: из 81933 sync-кандидатов валидный ADTS подтвердили только 25 (мусорные параметры Main/22050/stereo=5) — значит в payload старого файла реальные ADTS-фреймы почти отсутствуют (в WriteSample всё упало через первый байт-мусор).
- Вывод старой проверки «head=ff f1...» был уже не про payload — ADTS начили и во входном TS.
- Сообщение про «ASС с object type 4 (LTP)» из секции 3 — ОПРОВЕРГНУТО: csd-0 и LC; проблема ни разу не в профиле, а в смещении кадров.

## 8. Сессия 3 (19 окт 2026) — РЕМУКС ПОЧИНЕН, ЗВУК РАБОТАЕТ. Релиз v0.5.1

### 8.1 Главный вывод по багу «скачанное не проигрывается (3 fps, без звука)»
Корень проблемы найден **не в источнике, а в самом ремуксе** (коммит c251c04, «сквозной карвинг ADTS»):

- MediaExtractor на MPEG-TS отдаёт аудио **как есть** — ПЭС-пакеты, в которых лежат **сырые AAC-кадры без ADTS-заголовков** (проверено на эмуляторе: `s0 head=ff f1 50 80 03 9f fc…` — т.е. ADTS-заголовок в ПЭС-пакете ЕСТЬ, но extractor отдаёт сэмпл целиком, вместе с соседними кадрами).
- Код c251c04 пытался **разрезать каждый сэмпл на отдельные ADTS-кадры** (`splitAdtsFrames`). В сыром AAC-потоке регулярно встречаются **ложные синх-слова 0xFFFx** (случайные байты) → код резал поток по границам мусора → **аудиотрек портился, декодер AAC выдавал тишину** (на телефоне: `C2SoftAacDec: Invalid AAC stream` ×311, `AAC decoder returned error 0x0005, substituting silence`).
- Старый ремукс (432fecf) писал сэмплы экстрактора **как есть** — и его файл («Чёрный клевер») декодировался ffmpeg **без единой ошибки**.

**Итог: разбирать ADTS нельзя. AudioSpecConfig (csd-0) из экстрактора корректен (12 10 / 11 90) и менять его не нужно.**

Вторая половина бага — **PTS видео**: в MPEG-TS они немонотонны (B-кадры), MediaMuxer на этом пишет сломанный stts → ExoPlayer: `position=0`, уход в BUFFERING. Лечится CFR-таймлайном по видео.

### 8.2 Что сделано в `HlsDownloader.kt` (финальный вариант)
- Убраны `splitAdtsFrames` / `buildAsc` / `countAdtsFrames` и весь «карвинг» — аудио пишется **как есть** (`info.offset = 0; info.size = size`), PTS исходные.
- csd-0 берётся из формата экстрактора; если его нет — warning в лог.
- Видео — равномерный CFR-таймлайн: `pts = base + i * frameUs`, `frameUs = (maxPts-minPts)/(N-1)`.
- Два прохода (отдельные `MediaExtractor`): первый считает сэмплы/растяжку, второй пишет в `MediaMuxer`.

### 8.3 Проверка (эмулятор PIXEL_API_35, реальные файлы с телефона)

### 9.1 Почему кнопка «не работала» (проверено на эмуляторе, реальные файлы)
